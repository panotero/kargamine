On 2026-09-17, on top of the earlier CrmLead -> Prospect rename (`App\Models\Prospect`, `ProspectController`, `crm_leads`→`prospects` etc. — see git history around `2026_09_17_000000_rename_crm_leads_to_prospects.php`), a new phase added backend support for a 4-tab Prospect modal's Contacts and Requirements tabs:

- New tables: `prospect_contacts` → `prospect_contact_channels` (mobile/landline/email) + `prospect_contact_addresses` (links to an existing `prospect_locations` row, `restrictOnDelete`); `proposal_requests` (one-per-prospect, `RQ-YY-XXXXXX` code via `ProposalRequest::generateNextCode()`, mirroring `ClientMaster::generateNextCustomerCode()`'s lock-scan-retry shape) → `proposal_request_containers` (same column set as the legacy `prospect_containers_legacy` table, minus its retired free-text `origin`/`destination`/`convan_class`/`convan_size` columns).
- `Prospect::stageCompletionFlags()` gate 2 changed meaning: it used to be "has at least one legacy container", now it's "has at least one `ProspectContact`". Gate 3 (new) is "has at least one `ProposalRequestContainer` via `proposalRequest`". The legacy `prospect_containers_legacy`/`containers()` relation still exists and still has its own `saveStage2`/`storeContainer` endpoints, but is **no longer part of completion/promotion logic** — only `ProposalRequestContainer` rows count now. Don't assume `containers()`/`storeContainer` still gate anything.
- **Bug found and fixed in the brief's own suggested code:** `optional($this->proposalRequest)->containers()->exists() ?? false` fatals with "Call to a member function exists() on null" whenever `proposalRequest` is null — `Optional::__call` short-circuits to a bare `null` (not a wrapped Optional) once the wrapped object is null, so chaining `->exists()` onto that throws instead of returning null. Fixed to `$this->proposalRequest?->containers()->exists()` (PHP nullsafe operator) in both `stageCompletionFlags()` and `missingRequirements()`. Watch for this exact `optional($x)->relation()->exists()` pattern elsewhere — it's silently correct only when `$x` is non-null at every call site that's actually been exercised.
- **UPDATE 2026-09-17 (later same day):** the FK risk noted above was fixed. `prospect_contact_addresses.prospect_location_id` is now `cascadeOnDelete` (edited in place on the still-unshipped `2026_09_17_000014_create_prospect_contact_addresses_table` migration, not a new alter migration) — reasoning: `prospect_locations` rows are recreated with new ids on every Identity-tab save (`ProspectController::saveStage1` does delete-then-recreate on `$lead->addresses()`), so a contact→location link is inherently ephemeral and `restrict` broke both that resave and `Prospect::delete()`. Verified via tinker: created a prospect + contact + linked address, then `$lead->delete()` succeeded with no FK error.
- **Identity tab reconciliation (2026-09-17, same day):** the Identity tab only collects Source, Prospect/Company name, Business type, Relationship Manager, and Locations — contact-person name/mobile/email and the authorized-signatory block are no longer collected there (they live on the Contacts tab / are simply optional back-compat fields). `ProspectController::saveStage1` validation for `first_name`/`last_name`/`mobile` changed from `required` to `nullable`; `client_type` defaults to `'corporate'` server-side when omitted; `relationship_manager_id` (`nullable|integer|exists:users,id`) is now actually persisted via `$lead->fill()` (it was already `$fillable` and eager-loaded but silently dropped before). `Prospect::stageCompletionFlags()` gate 1 ("Identity complete") no longer checks `first_name`/`last_name`/`mobile`/`mobile_type` or any authorized-signatory field — only `source`, `client_type`, `company->company_name`, `company->type_of_business` (corporate only), and one complete address. `missingRequirements()` updated symmetrically (dropped the same entries). Authorized-signatory columns/fields are still accepted/stored (not removed) — just no longer gate completion or appear as a missing-requirement.
- `AddressTypeSeeder` gained `'Main Office'` (the new Identity tab defaults new locations' `address_type` to that value, which previously wasn't a seeded LOV option and would've silently blanked).
- The old standalone `/page_crmLeadForm` route + `PageController::page_crmLeadForm()` were removed (frontend had already deleted `pages/crmLeadForm.blade.php`) — that logic now lives entirely in the prospect modal.
- `LovController` methods (incl. the new `title()`) still return a bare `Option->values` collection, not the `{success,data}` envelope — intentional, matches every other LOV endpoint (see [[project_client_master_rebuild]] for the same note from an earlier phase).
